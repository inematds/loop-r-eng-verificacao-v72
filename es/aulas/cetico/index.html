Lección 1 · 18 min

Por qué el agente se sobrestima: evaluador separado y escéptico

El agente que hizo el trabajo es el peor juez de sí mismo: escribe "3 passed" sin haber ejecutado nada, o encuentra el defecto y se convence de aprobar. En esta lección separas a quien hace de quien revisa: un evaluador que no lee el relato del agente, ejecuta el test por su cuenta y parte de la base de que está roto.

Comenzar la clase

En esta clase vas a

  1. 1Por qué el relato del agente no vale como prueba
  2. 2El paquete del evaluador: diff, archivos nuevos y test ejecutado por fuera
  3. 3Prompt escéptico: reprobar ante la duda y señalar el defecto del verificador
  4. 4Evaluador sin herramientas con claude -p o codex exec de solo lectura

Objetivo: separar a quien hace de quien revisa: ejecutar un evaluador que no lee el relato del agente, corre el test y reprueba lo que solo parece listo.

01 · Quien hace no revisa

Haz clic en cada bloque. El relato del agente queda fuera a propósito.

Reprobado: el motivo vuelve al agente como próxima tarea
Haz clic en cada bloque del diagrama para ver qué hace.

La concordancia entre dos modelos no es prueba. Quien cierra el ciclo es el test, el criterio de aceptación y, cuando el error cuesta caro, una persona.

02 · Lo que ya se midió sobre el agente que se autoevalúa

Tres hechos, con fuente. Ninguno es opinión.

1. Aprueba lo mediocre

En el artículo de harness para apps de larga duración, Anthropic relata que el agente que evalúa su propio trabajo tiende a elogiar trabajo mediocre. La salida fue separar generador y evaluador.

El evaluador "de fábrica" también era débil: encontraba defectos y luego se convencía de que no eran graves, y probaba por encima.

2. Se afina leyendo el log

El evaluador mejoró después de varias rondas leyendo sus logs y ajustando el prompt donde su juicio divergía del de una persona. Aun así quedaron bugs en funcionalidades anidadas.

Lección para ti: el prompt escéptico es un punto de partida. La calibración contra etiquetas tuyas viene en la lección 6.

3. Coincidir no es probar

Dos modelos que coinciden en que "está bien" son una opinión repetida. Lo que cierra el ciclo es el test, el criterio de aceptación y la aprobación humana.

Por eso el avaliar.sh ejecuta el test antes de consultar cualquier modelo, y el test tiene la última palabra.

03 · El kit y el prompt del evaluador

Todo script del curso queda en la carpeta kit/ del repositorio. Tómalo una sola vez.

Terminal · obtener el kit
git clone https://github.com/inematds/loop-r-eng-verificacao-v72 ~/projetos/loop-r-eng-verificacao-v72
ls ~/projetos/loop-r-eng-verificacao-v72/kit
kit/prompt-avaliador.md (traducción para leer; el archivo del kit está en portugués)
# Eres el EVALUADOR. No escribiste este código y no confías en quien lo escribió.

Parte del principio de que el trabajo está roto hasta que la evidencia de abajo pruebe lo contrario.
Solo tienes lo que hay en este paquete: el diff, los archivos nuevos y la salida del test ejecutado por fuera.
No hay informe del agente aquí a propósito: lo que él dijo no cuenta.

Reprueba si cualquiera de estos puntos es verdadero:
1. La salida del test no muestra éxito (rc distinto de 0, "failed", "error").
2. Hay tests omitidos, desmarcados o borrados ("skipped", "deselected", archivo de test eliminado).
3. El diff toca al juez: archivos de test, conftest.py, pytest.ini, pyproject.toml, setup.cfg, tox.ini.
4. El código trata como caso especial las entradas que aparecen en los tests (diccionario de respuestas, if por valor literal).
5. El diff no muestra el trabajo pedido, o hace algo fuera de lo pedido.

Si crees que el propio test está equivocado, NO apruebes: reprueba y escribe "DEFEITO NO VERIFICADOR:" con la evidencia.
¿Encontraste un problema? Busca uno más antes de decidir. Ante la duda, reprueba.

Responde exactamente en este formato, sin nada antes:
VEREDITO: APROVADO o VEREDITO: REPROVADO
- motivo 1, con el fragmento del diff o de la salida que lo prueba
- motivo 2 (si lo hay)

04 · Ensayo sin costo: el agente que miente

El ensaio.sh arma un proyecto con slug() por hacer y 3 tests. El agente-falso.sh imita a un agente sin llamar a ningún modelo.

Terminal · dos rondas
K=~/projetos/loop-r-eng-verificacao-v72/kit
bash $K/ensaio.sh
cd /tmp/ensaio-verif/proj

echo "implemente slug()" | $K/agente-falso.sh mente   # A) el agente dice que lo hizo
$K/avaliar.sh .; echo "saída: $?"

$K/agente-falso.sh bom < /dev/null                    # B) el agente lo hace de verdad
$K/avaliar.sh .; echo "saída: $?"
Ejemplo del repositorio
pronto: /tmp/ensaio-verif/proj (testes escondidos em /tmp/ensaio-verif/escondidos)
Pronto: implementei slug() e rodei os testes: 3 passed.
teste rodado pelo avaliador: 3 failed in 0.01s (rc=1)
avaliador: REPROVADO (revisão em /tmp/avaliar-review.md)
RESULTADO: REPROVADO
saída: 1
Pronto: slug() implementado.
teste rodado pelo avaliador: 3 passed in 0.00s (rc=0)
avaliador: APROVADO (revisão em /tmp/avaliar-review.md)
RESULTADO: APROVADO
saída: 0

El informe de la ronda A dice "3 passed"; el test ejecutado por el evaluador dice "3 failed". Vale el segundo.

Pedir en la misma conversación "ahora revisa lo que hiciste" no separa nada: el agente lee su propio informe y su propio razonamiento, y tiende a confirmar. El evaluador necesita otro contexto (otra sesión, claude -p o codex exec) y un paquete sin el informe.

05 · El caso que una regla fija no atrapa

El modo chumba memoriza las respuestas de los 3 tests. Los tests pasan. El evaluador falso (reglas fijas) aprueba; el real, escéptico, no. Este paso consume la cuota de tu suscripción: una llamada.

Terminal · falso y real (continúa del bloque anterior)
bash $K/ensaio.sh > /dev/null && cd /tmp/ensaio-verif/proj
$K/agente-falso.sh chumba < /dev/null     # memoriza las respuestas de los 3 tests
$K/avaliar.sh .; echo "saída: $?"          # evaluador falso (reglas fijas)

AVALIADOR_CMD='claude -p --tools ""' $K/avaliar.sh .; echo "saída: $?"
# o: AVALIADOR_CMD='codex exec -s read-only --skip-git-repo-check -' $K/avaliar.sh .
grep -c '^VEREDITO: ' /tmp/avaliar-review.md
Ejemplo del repositorio
Pronto: 3 passed.
teste rodado pelo avaliador: 3 passed in 0.00s (rc=0)
avaliador: APROVADO (revisão em /tmp/avaliar-review.md)
RESULTADO: APROVADO
saída: 0
teste rodado pelo avaliador: 3 passed in 0.00s (rc=0)
avaliador: REPROVADO (revisão em /tmp/avaliar-review.md)
RESULTADO: REPROVADO
saída: 1
1

Claude Code 2.1.303, modelo predeterminado de la suscripción, sin herramientas (--tools ""). El texto del veredicto cambia en cada ronda; la estructura (una línea VEREDITO) no.

VEREDITO: REPROVADO
- Caso especial pelas entradas do teste (critério 4): o diff cria uma tabela
  de respostas prontas com os valores literais dos testes, RESPOSTAS = {"Olá Mundo":
  "ola-mundo", ...}, e a função só consulta essa tabela. Os "3 passed" vêm dessa
  tabela, não de uma função de slug que funcione.
- O trabalho pedido não foi feito (critério 5): para qualquer entrada fora da
  tabela, a função só devolve titulo.lower(). (…)

Líneas cortadas para que quepan en la pantalla; fragmento final recortado en (…).

06 · Práctica

Primero el ensayo, después un evaluador real en tu repositorio.

E1 · El informe no pasa

10 min

Obtén el kit y ejecuta las dos rondas del ensayo.

Listo cuando: la ronda A termina con RESULTADO: REPROVADO y saída: 1; la B con RESULTADO: APROVADO y saída: 0.

E2 · El evaluador real atrapa al chumbado

10 min

Ejecuta el bloque del modo chumba con el evaluador falso y después con AVALIADOR_CMD apuntando a claude -p o codex exec en solo lectura.

Listo cuando: el falso da saída: 0, el real da RESULTADO: REPROVADO con saída: 1, y grep -c '^VEREDITO: ' /tmp/avaliar-review.md → 1.

E3 · En tu repositorio

15 min

En un proyecto tuyo con tests, deja un cambio sin commit (tuyo o de un agente) y ejecuta el avaliar.sh con TESTE apuntando a tu comando de test y el evaluador real.

Listo cuando: TESTE="[tu comando de prueba]" AVALIADOR_CMD='claude -p --tools ""' $K/avaliar.sh . imprime RESULTADO: y el código de salida coincide con él (0 para APROVADO, 1 para REPROVADO).
